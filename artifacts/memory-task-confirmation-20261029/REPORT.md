## 正確さと再利用の照合

- 修正後の比較18/18で成功条件と必須事項を保持。確認あり9/9で、実際の質問ID・模擬回答・PostToolUse・実操作・成果物を照合した。確認前の作業、範囲外操作、誤った完了、欠測は比較18件で0。
- 既存成果で完了の3件は読取・書込とも0。元の担当者authorの実モデル成果を、別利用者memberへの明示grantで提示し、権限・原本ID/版・出典バイト・環境/実装・期限・成果物ハッシュを確認した。原本のモデル利用として数えていない。
- 差分3件は読取単位9→3。既存の6単位を一字も変えず、新しい3単位だけを調べた。成果物全体の必須事項は維持した。読取・書込の呼出回数は各3回のまま。
- 全体実施3件は全9単位を新しく読み、全体を作り直した。再利用による新規処理の省略はない。
- 3種類×3選択それぞれ1組の小規模な合成比較。統計的な再現性、一般の調査品質、実メンバーの選択や再作業発生率を証明するものではない。数値は当回の実測値。

## 初回の失敗と修正

CLI 2.1.311では、PreToolUseの回答フックだけでは非対話-p実行にAskUserQuestionが公開されなかった。初回の確認あり1件は未回答で停止し、新規操作0を維持した。この失敗と旧条件の対照を残して費用に計上した。両条件へ --permission-prompt-tool stdio を指定し、同じフック・原本・成功条件で9組を比較し直した。権限チェックの省略は行っていない。詳細はrecovery.json。

独立監査で、数値直後の文末ピリオドを小数と誤認する判定不具合を発見。失敗テストを追加し、40.を許可、400/40.5を拒否するよう修正した。モデル出力や課題は変更せず、再集計のみで解消した。

## 導入判断と次の改善

登録済み対象での確認フローを条件付きで利用できる状態とした。作業全体を終えられる候補の提示を優先する。今回の短い課題では差分・全体実施を効率改善として採用しない。既存成果の受入、差分実施、全体実施を区別する確認機能として維持する。

通常プロジェクトの設定と既存の無関係な変更を保持した。task_workflowsへの実業務用の対象登録はまだなく、未登録の通常作業には確認を追加していない。再利用時はdocs/MEMORY_REUSE_TASK_CONFIRMATION.mdの設定手順を使う。クラウド展開、push、実メンバーへの通知は行っていない。

次の効率改善候補は、ユーザーの選択をモデルへ一往復させる前にローカルの確認画面で受け取り、選択済みの最小情報だけで作業を開始する方法。ただしネイティブ入力の証拠、権限、変更検知、差分範囲の制限を維持する必要がある。この方式は今回未実装・未測定。

## 証拠

- report.json: 選択別・種類別の4区分トークン、時間、費用、全9組の対応。
- audit.json: ネイティブ呼出、利用者回答、原本/成果/権限/期限、差分保持の別実装による監査。比較18/18合格。全23実行では22/23合格、初回の未回答失敗1を残す。
- runs/<id>/: 実CLIログ、実操作、設定、原本、SQLite証拠、成果物、模擬回答。
- runtime/r32/manifest.json: 評価時の固定実装。通常実装への変更と評価スナップショットを区別。
- PROTOCOL.md / recovery.json / budget-proposal.json: 固定条件、修正、承認上限。
