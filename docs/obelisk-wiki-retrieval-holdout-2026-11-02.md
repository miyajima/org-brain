# Obeliskを参考にしたWiki検索の改善と追加比較（2026-11-02）

## 状態

検索条件の追加と原本の該当箇所を読む機能を実装し、ローカル検証と未使用12問の再比較を完了した。
全項目正答はObeliskが11/12問、OrgBrainは変更前・変更後とも3/12問。
今回の機能追加による回答精度の改善は確認できなかった。
変更後の自動的な絞り込み・抜粋選定を標準手順にする根拠は得られず、機能は任意指定のままとする。
既定の検索方法は維持し、導入先ランタイムの更新・本番配備は行っていない。

追加36件の外部送信は一度自動承認レビューで拒否された。その後、ユーザーが
「この抜粋をOpenAIへ追加36回送信して比較を実行」と明示的に許可し、固定した36件だけを実行した。

## 実装した機能

| 機能 | 目的・注意点 |
| --- | --- |
| 複数語のAND/OR検索 | `match_mode=all/any`。既定のフレーズ検索は維持。最大8語。 |
| 対象の絞り込み | `page_id`、`source_id`、`path_prefix`、`heading`。必要なページとその出典をたどる。 |
| 期間の絞り込み | `since` 以上、`until` 未満。対象はページ改訂日時／原本の取り込み日時。本文に書かれた出来事の日付ではない。 |
| 同じ資料からの件数制御 | `per_owner_limit`。一つの資料ばかりが検索結果を占める状況を調整する。 |
| 原本の該当箇所を読む | `source_read` に `query`、`section`、行範囲、前後の行数を指定。該当箇所がないときは明示する。 |
| 続きを安全に読む | 文字数制限やMCPのトークン制限後も実際の開始位置・継続位置を返す。原本の版とハッシュ検証は保持。 |

実装は `packages/wiki-engine/src/lib.rs`、CLI/MCPの公開入口は
`packages/orgbrain-cli/src/lib/wiki-cli.mjs` と `wiki-mcp.mjs`。
使用方法と制限は `docs/LOCAL_KNOWLEDGE_WIKI.md` を参照。
セッション全文の自動保存は追加していない。

`project_id` は資料の所属ラベルに対する厳密な条件で、内容の関連性を示す条件ではない。
複数のプロジェクトにまたがる個人Wikiでは、省略してページや出典で限定する。
検索候補数には既存の上限があり、大規模なWikiでの網羅性や速度は未検証。

### 原因を分けて確認したこと

- **保存資料の不足**: 対象コミット `6a48c20` の記録は、固定33ページと引用原本272件の本文から見つからなかった。
  Obeliskのセッションには該当する報告があり、Node146件・Python42件などを答えられた。
  検索条件だけでは、保存されていない報告を取り戻せない。
- **保存済みの事実の取り出し不足**: 互換性問題の「16,000文字上限」と、原因分析の
  「47→51回、約3,380→4,757トークン」は固定した引用原本に残っていたが、両Wiki条件の回答入力に入らなかった。
  全項目の正解が保存されていると証明したわけではないが、少なくともこの部分は取り出しの問題である。
- **絞り込みの強さと順位付け**: 新しい比較手順は上位3ページ・最大12出典候補へ絞ってから該当箇所を読む。
  質問の語と異なる表現で残る資料、背景説明・後続訂正を落とす場合があった。
  これらは実験用の固定手順の制限で、追加した検索APIだけの因果効果は分離できない。

今回の結果からは、任意の絞り込み機能を足すだけで通常の回答精度が上がるとは言えない。
標準手順に採用する前に、検索語の言い換え、候補の順位付け、時点の照合を別に検証する必要がある。
Wikiへ記録する際も、最終結論だけでなく、重要な数値・未確認事項・訂正を出典と結び付けて残す余地がある。
これらの追加改善や追加モデル評価は今回は行っていない。
