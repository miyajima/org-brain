# 従来検索・AMP・Living Brainの比較（2026-11-09）

**現行AMP 0.1を従来検索の代わりに使うことは、この範囲では勧められない。** 実資料を固定した16問では、必要な情報が条件・例外まで揃った質問は従来検索14/16件、AMP専用検索4/16件だった。平均返却トークンはAMPで4.9%増えた。一方、AMP形式のページを従来検索にも加えた場合は15/16件で、記述規約と検索方式を分けて評価する必要がある。

これは1テーマの検索結果の評価であり、製品全体の回答正答率ではない。Living Brainは同一データで実行できていないため、公開仕様を比較した。

## 何を比較したか

対象は個人Wikiの「記憶はどこから入り、いつ使えるようになる？」、その版付き原本13件（実装コードと実セッション・運用の検証報告、計218,416バイト）、作成済みAMPインデックス1件と下層メモリ5件。原本のバイト列は元のSHA-256と一致確認した。生セッション履歴は新たに読んでいない。

| 方式 | 検索対象 | 実行した入口 |
|---|---|---|
| A 従来検索 | 元のテーマページ1件＋原本13件 | `orgbrain_wiki_recall` |
| B AMPページ追加＋従来検索 | A＋AMPインデックス1件＋下層5件 | 同じ`orgbrain_wiki_recall` |
| C AMP専用検索 | Bと同じデータ | `orgbrain_wiki_amp_search` |

Aを複製してB/Cを作り、共通原本とチャンクのIDも同じにした。個人Wiki本体は測定中に変更していない。Cには事前定義した既知条件`facts`も渡した。A/Bの入口に同じ条件引数はない。この違いは実際のAPIの比較であり、検索アルゴリズムだけを切り離した試験ではない。

各問を短いキーワードと自然文の2形式で実行し、返却予算は1,200/4,000トークン、上限5結果。16問×2形式×2予算×3方式＝192回。生成モデル呼び出しは0回。現行チェックアウトの関数を実際のMCPディスパッチから呼んだローカル検証であり、常駐MCPの更新・デプロイはしていない。

## 採点の意味と限界

- 質問は実資料から事前に作成した。既存のAMPに直接対応する通常質問4件、例外に当たる質問6件、原本にあるが独立したAMPメモリを用意していない質問6件。独立した評価者や未知の実ユーザー質問による検証ではない。
- 16の主要情報と27の条件・例外・検証限界を必須項目として固定した。返却された本文・メモリ・原本抜粋に必要項目が全てある質問を「情報が揃った」と数えた。除外理由だけの診断値は回答の根拠に数えない。
- 自動採点は事前の表現パターンを使う。原文監査でq09のハッシュ照合表現2項目とq16の「隔離DBと模擬API」1項目の同義表現を補った。全192応答に同じ補正を適用し、6行の採点が変わった。元の採点、補正、応答のハッシュは保存した。検索の再実行や入力の変更はしていない。
- 「検索精度」はここでは必要情報の取得率。生成回答の正しさ、一般的なランキング適合率、意味的な完全性、誤った手順を実行しない能力までは測っていない。正規表現の採点にも限界がある。
- トークンは`o200k_base`で測った応答JSON全体。メタデータと引用を含む。生成モデルの請求、システム指示、索引作成・更新、質問からキーワードやfactsを作る費用、追加検索、回答生成は含まない。トークン効率と料金削減は同じ意味ではない。

## 小さい返却予算と自然文の境界

| 1,200トークン、同じキーワード | A | B | C |
|---|---:|---:|---:|
| 必要情報が揃った質問 | 8/16 | 6/16 | 1/16 |
| 条件・限界の取りこぼし | 15/27 | 18/27 | 24/27 |
| 平均返却トークン | 666.31 | 497.44 | 486.56 |

Cの小さい値は十分な情報を返せなかった結果を含むため、効率改善とは扱わない。現在はメモリ全文、構造、根拠抜粋を一度に返し、予算超過時にメモリ全体を外す。

日本語の自然文をそのままツールへ渡す追加検証では、A/Bは両予算で0/16件。従来実装は空白で検索語を分けるため、空白のない質問文が長い1語になる。Cは両予算で15/16件が`invalid_query_terms`。AMP側が最大16語を許す一方、内部検索エンジンの`any`検索は最大8語で、上限が一致していない。残り1件は4,000トークンでは取得できた。

これは**ツールへ直接自然文を渡したときの入口の問題**であり、エージェントがキーワードに変換する通常の会話検索全体が0%という意味ではない。エラー応答の短さをトークン削減に数えない。

## 原因と改善候補

1. **「適用しない」と「説明に使わない」を分ける。** q03〜q09の例外6問では、例外に該当するメモリが本文ごと除外された。例えば「学習offならどうなる？」に必要な「offならスキップする」という説明も消える。`explain`では不適用の理由と根拠を返し、`apply`では手順の採用を止めるという分離が候補になる。
2. **原本・通常ページへの補完検索を残す。** 原本13件には答えがあるが、現行AMPは5メモリしか独立した検索結果にしない。質問に対応するメモリがない場合に、原本へ戻る仕組みが必要。
3. **候補の検索と本文の取得を分ける。** 索引でID、短い説明、適用状態、根拠位置を返し、選んだメモリを条件・例外とともに読む。原本の長い抜粋は必要時に取得する。ただし要約だけで実行せず、最終判断の前に条件を読む契約を保つ。
4. **検索語の8/16語の不整合を修正する。** 質問の切り分け、複数回の検索と重複排除などを検討する。索引の共通タイトルだけで別の記憶が大量に候補になる順位付けも再検証する。
5. **次の評価は今回の16問とは別に固定する。** 通常・例外・未整備の各群、未知条件、古い版、小予算を含む質問を用意し、検索だけでなく最終回答の条件の保持と総トークンを確認する。

以上は提案。今回の測定では製品の検索ロジックや既存AMPページを書き換えていない。

## Living Brainとの再比較

Living BrainはChatAndBuildの`livingbrain.com`を対象に、2026-11-09時点の公式資料を再確認した。接続済みツールがなく、同じ私有資料を投入して測定していない。下表は公開契約と、手元で読んだAMP実装の比較である。

| 観点 | Living Brainの公開仕様 | 今回のAMP 0.1 | 取り入れる候補 |
|---|---|---|---|
| 検索 | 意味検索＋キーワード検索。既定topK=5、minSimilarity=0.35。キーワード一致は閾値以下でも返す | キーワードで索引・メモリを探索し、既知条件で除外 | 検索経路を併用し、例外や固有語を落とさない |
| 読む量 | 短い索引、検索結果からページを選び本文を読む手順 | メモリ全文と原本抜粋を一度に返す | 検索→必要な本文→追加根拠の段階取得 |
| 再利用の単位 | Markdownページ。タイトル、要約、種類、状態、版、出典参照 | 問いの索引＋主張単位のメモリ＋固定原本 | 人が読めるテーマページと機械的な適用条件の両立 |
| 条件・例外 | 公開Search APIにAMPのfacts/例外式に相当する入力は見当たらない | 明示的な条件・例外。ただし該当時に本文も除外 | 条件を明示する規約は維持し、説明用の取得を止めない |
| 根拠 | ページ版、取り込み元ID、チャンクUUID等 | source ID・版・SHA-256・行範囲を照合 | 来歴を保つ。公開資料にない同等のハッシュ保証を推定しない |

検索の公開契約は[Search Pages](https://docs.livingbrain.com/api-reference/workspace/search-pages)。MCPの検索→ページ選択→読み取りは[Sign in with MCP](https://docs.livingbrain.com/mcp/sign-in)。[Prompt Index](https://docs.livingbrain.com/api-reference/workspace/prompt-index)は要約を160文字に制限した一覧で、pinnedを優先し、deprecated/archivedを隠す。この短い索引だけで条件・例外が残るという保証は確認していない。[Get Page](https://docs.livingbrain.com/api-reference/workspace/get-page)は本文、版、出典の取り込み元ID・チャンクUUID等を返す。

Living Brain公式サイトは内部LoCoMo評価で92.2%を掲げるが、1,540問の回答採点であり、今回の16問・検索結果内の情報取得率とは分母も手順も違う。公表値を横並びの実測値にはしない。Living Brainの同条件での検索精度、返却トークン、例外の取りこぼしは**未測定**。[公式の評価説明](https://livingbrain.com/)

今回の結果からは、**AMPの記述規約を維持し、従来検索を残しながら、Living Brainにある段階取得を参考にする**構成が次の候補になる。性能改善は実装後の別評価で確かめる。
