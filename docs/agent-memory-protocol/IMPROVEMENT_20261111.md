# AMP検索の補完・例外説明・段階取得（2026-11-11）

## 結果

AMPの文書形式`amp/0.1`は維持し、検索契約を`retrieval_version:0.2`へ更新した。従来検索の併用、適用できない理由の説明、候補→本文→根拠の読み分けを実装した。前回と同じ16問のキーワード検索では、本文をまとめて返す設定で16/16問の必須情報が揃い、条件・例外・限界27項目も取得できた。

省トークンは達成したとは言えない。本文一括の平均返却は3,529.94トークンで従来検索より29.1%多い。段階取得の固定手順では平均2,893.94トークン、14/16問で、本文一括より情報を落とした。未知の質問による一般的な精度や回答生成の正しさは未測定。

## 前回の低下と「AMP化していない」の意味

前回下がったのは、AMP専用検索だけに切り替えた場合の取得率。元資料や従来検索を壊したという結果ではない。従来検索は14/16、AMPページを加えた従来検索は15/16、当時のAMP専用検索は4/16だった。

最初の試作では、テーマの全内容を自動変換せず、5件だけをAMPメモリとして整理した。原本13件にあるClaude Codeの試験、予算不足、埋め込み保留などの情報には独立したAMPメモリを用意していなかった。専用検索がその未整備部分へ戻らなかったことが問題で、文字抽出・記憶抽出の品質低下を測定したものではない。

今回も全資料の自動AMP化は追加していない。通常ページ・保存原本を併用して、AMP形式への整理が済んでいない内容も検索対象に残した。既存5メモリの本文や固定評価の原本は変更していない。

## 実装したこと

```text
質問・既知の条件
       ↓
AMP索引・メモリ検索 ＋ 従来のページ・原本検索
       ↓
短い候補（不適用なら、その理由も表示）
       ↓ 選んだ候補を読む
本文：主張・理由・条件・例外・手順・限界
       ↓ 根拠が必要なら読む
固定された原本の版・ハッシュ・行範囲を照合
```

- `amp-search` / `orgbrain_wiki_amp_search`は既定で`mode:explain`、`detail:summary`。同じproject/path範囲で従来recallを併用する。非AMP資料は別のkindで返し、条件照合済みのAMPへ昇格しない。明示path、applyモード、fallback無効時は補完しない。
- 例外や条件不一致は説明検索では`not_applicable`と具体的な理由を返す。`mode:apply`では引き続き除外し、原本も照合する。不明な条件は`unknown`のまま。
- `amp-read` / `orgbrain_wiki_amp_read`を追加。検索時の`expected_hash`と同じ版の本文を読み、改版されていれば停止する。通常は根拠参照だけ、`include_evidence:true`で原本抜粋も照合する。本文だけでは原本の一致は`not_checked`。
- `detail:memory`は条件や例外を落とさず本文を一括取得する。`detail:evidence`は原本も含める。予算不足では結果全体を省き、条件だけを切り落とさない。
- 自然文の検索語は最大64語、内部検索は8語ずつ。短く空白で区切った複合キーワードはそのまま使う。索引の共通タイトルによる無関係な候補の押し上げをやめ、主要な主張の一致を留保だけの一致より優先する。
- 既存の`wiki search` / `wiki recall`の処理は変更していない。段階取得の原本参照では、従来抜粋の末尾改行による余分な行番号を補正した。

## 追記：予算超過時に結果を空にしない（2026-11-12）

1,200トークンで必要情報が揃わなかった質問のうち、キーワード検索6問・自然文8問は結果が0件だった。原因は2つある。予算を超えると結果を丸ごと外す処理と、補完する原本の抜粋が予算に関係なく1,800文字だったことである。そのため、上位1件が入らないと何も返らなかった。段階取得では、要約の候補に既定値の引数などが毎回付いて重く、必要な候補が外れていた（q12）。

変更は`agent-memory-protocol.mjs`だけで、入力スキーマ・`wiki recall`・既存のAMPページは変更していない。
- 収まる上位の結果は本文のまま返す。外れる結果は要約か読み出し参照（`requires_read:true`、`next_read`付き）に置き換えて残し、件数を`degraded_results`に返す。要約検索では候補数を優先し、低順位から参照に縮める。apply用の参照は`mode:apply`と原本照合付きで読み直す。
- 本文検索では、補完する原本の抜粋を返却予算の半分（最大1,800文字）にする。要約検索では短くしない。短くすると`next_read`で読む行範囲まで狭まるためである（初回の再評価でq11・q16が悪化して判明）。
- 要約の`next_read`から既定値（`mode:explain`、空のfacts、`include_evidence:false`）を省く。例外や限界の文で一致した場合は、`matched_on`と`matched_text`でその文を示す。

同じ固定データ・質問・採点で再評価した。現在のWikiエンジンは11/11の評価後に再ビルドされている（検索部分の差分は変数の受け渡しの整理のみ）。そのため、変更前のコード（HEAD `53e1944c`）も同じエンジンで再実行し、11/11の集計と完全に一致することを確かめてから比較した。
