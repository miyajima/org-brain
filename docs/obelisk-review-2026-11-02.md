# Obeliskの実装・評価とOrgBrainへの取り込み候補

調査日: 2026-11-02。対象は `tommy0103/obelisk` のコミット
`1f8205b5b600516fe09ebea80d6983bcac1082b8`（2026-11-01 UTC）。
OrgBrainの比較対象は調査時点の作業ツリーであり、未コミット変更を含む。
この調査では製品の動作、設定、既存セッションの保存方法は変更していない。

## 結論

Obeliskから取り込みたいのは、過去の会話を構造を保って探し、必要な箇所だけ原文に戻れる仕組みである。
「全履歴を保存すれば、どのモデル・どの作業でも強くなる」という証拠は確認できなかった。
公開比較では会話履歴QAで通常の検索より良い結果がある一方、コード修正では改善が確立していない。
順位の真偽は採用判断の対象とせず、公開された比較条件・実装・今回の動作確認から評価する。

OrgBrainには既にBM25（検索語の一致を使う順位付け）、検索単位、時間条件、追加検索がある。
したがって、検索方式を丸ごと置き換えるより、原文への参照と小さな追加読み出しを足して測る案を優先する。

## 2. 実装上の工夫

```text
各ツールが残したローカル履歴
        ↓ providerごとに共通の形へ変換
SQLite: セッション / 発言 / ツール実行 / 親子関係 / 要約
        ↓ プロジェクト・期間・発言の種類で絞る
全文検索で候補を発見
        ↓ 選んだ発言の前後・親発言だけ読む
モデルが原文を確認して回答

承認済みの結論は別のmemory層 → 次回の入口として使う
```

### 2.1 原文と結論を別に持つ

`schema.sql`には`messages`、`tool_calls`、`tool_results`、`subagents`、`summaries`などがある。
`memories`は、承認済みMarkdownファイルへの参照、英語の概要、出典セッション・発言範囲を持つ。
抽出時に落とした情報へ戻れる点が、結論だけを残す仕組みより強い。
ただし原文に書かれた発言・計画が、そのまま実行済みの事実になるわけではない。

### 2.2 モデルが質問に応じて検索を組み立てる

検索エンジンの中心はSQLite FTS5の語句検索と`rank`順であり、確認した検索経路に
埋め込みベクトルや別モデルの再順位付けはない。
モデルはJSから`search()`、`sessions()`、`messages()`、読み取り専用の`sql()`を組み合わせる。
日付・プロジェクト・ファイルなどが分かる場合は、その条件で先に絞る。
質問の言い換えや、最初の検索で見つけた語句を使った追加検索ができる。

スキルは「候補を探す → 必要な箇所だけ読む → 重複を除く → 短い根拠を返す」を具体的に教える。
検索結果を渡すだけでなく、検索の手順を改善する設計になっている。

### 2.3 時間の近さと親子関係を区別する

`messages()`は指定発言、前後の有限窓、セッション内のページ読み出しに対応する。
時刻が近い発言と、親発言をたどった経路は別の関係として扱う。
既定の前後窓は各3発言、指定件数は0〜500。非表示の発言を結果に出さず、親経路の循環も検出する。
元データに確定した分岐がない場合、将来方向の経路を推測しない点も良い。

### 2.4 証拠の種類を失わない

`content_type`、`is_meta`、`visibility`、`source`を保持する。
制御用メッセージは既定で除外し、取り消された履歴は明示した場合だけ返す。
実行中の自分のセッションは`is_invoking`と表示する。
ただし表示だけで自動除外はしない。また通常の`search()`は思考用テキストも返し得る。
「発言」「提案」「実行結果」の区別は、呼び出し側にも責任が残る。

### 2.5 更新を小さくする

Codex用の通常経路では、同じファイルの末尾に追加された部分だけを読む。
ファイルの識別情報、完全な行の境界、サイズなどを検査し、条件が外れた場合は検証または全体読み直しへ戻る。
通常経路は既存部分が書き換わらないという前提を置くため、毎回全文を検証する経路とは保証が違う。

[2026-09-17の速度報告](https://github.com/tommy0103/obelisk/blob/1f8205b5b600516fe09ebea80d6983bcac1082b8/docs/codex-cooperative-offset-benchmark-2026-09-17.md)では、
84.8〜169.1 MiBの5履歴に262 Bを追加した条件で、解析・保存の中央値が187.78〜466.22 msから0.72〜0.97 msになった。
単一マシン、warm cache、メモリ内SQLite、7サンプルでの測定。検索・監視・索引更新全体の速度ではない。
全体読み直しへの後退経路は、旧版より1.8〜4.4倍遅いという負の結果も明記している。

### 人工データの確認

[再実行用スクリプト](../artifacts/obelisk-review-20261102/probe.mjs)と
[結果](../artifacts/obelisk-review-20261102/probe-results.json)を保存した。

| 確認 | 実際の結果 | 意味 |
| --- | --- | --- |
| 1万文字の実行ログ12件を検索 | 12ヒット+前後72件、JSON **857,530文字** | 件数制限だけでは文章量を制限できない |
| 同じヒットをID・種類・240文字の抜粋へ整形 | JSON **3,843文字** | モデルへ渡す前の投影・重複排除が重要 |
| 前後1件ずつの窓 | 3発言、JSON **41,499文字** | 窓の件数上限に加え、各本文と合計量の制限が必要 |
| 日本語の連続した文章から「認証障害」を検索 | 全文一致1件、部分一致0件 | 既定の語句分割を日本語向けにそのまま採用できない |
| `memories({query:'認証障害'})` | 英語を要求してエラー | memory層の英語前提を日本語のOrgBrainへ移植しない |
| 10,013文字の末尾にだけある語句 | 索引は10,000文字、末尾の語句は0ヒット | 原文全部がSQLiteに検索可能な形で残る設計ではない |
| 通常の証拠検索 | 可視の本文とthinkingを返す | 種類を確認せずユーザーの確定意思と扱ってはいけない |
| 自分の実行中セッション | フラグ付きで検索結果に残る | 独立した過去の証拠から除く処理が別途必要 |

この人工データは文章量と境界の再現用であり、実ユーザーの平均負荷や作業成功率ではない。
`search()`は各ヒットに最大6件の近傍全文を付けるため、同じ文章が重複して膨らむ。
`messages()`も本文自体の文字数を制限せず、anchorは独立フィールドと配列の両方に入る。
新しいAPIとスキルには改善があるが、古い評価の弱点が解決したかを示す現行版のQA再評価は確認できない。

### 「全セッション保持」の範囲

対象は、設定されたローカル保存先に残り、対応形式として読み取れる履歴。
Claude/Codex共通処理の`TEXT_LIMIT=10000`、Codex本文・実行結果の`trunc()`を確認した。
それ以降の語句は通常の全文検索に出ない。`raw()`は元のprovider記録に戻る方式で、元ファイルが必要になる。
消された元履歴や未対応形式を含む、独立した完全バックアップと考えてはいけない。

## 4. OrgBrainとの差と取り込み候補

現行の主な比較先:

- `packages/orgbrain-cli/src/codex-session-import.mjs:358`: 履歴から候補を抽出する経路。
  歴史上の最終回答は確認待ちへ回し、原文・思考・実行ログを永続保存しない設計。
- `packages/shared/src/memory-retrieval.ts:795`: 検索単位のBM25、時間条件、出典情報を用いた検索。
- `packages/orgbrain-cli/src/lib/context-search-followups.mjs:68`: 不足がある場合の有限回の追加検索。
  元の範囲を引き継ぎ、情報が増えない・期限超過などで停止する。

比較はこれらの経路に限る。OrgBrain全体の原文保存の有無を、この調査だけで断定しない。

| 優先度 | 取り込む候補 | OrgBrainで足す点 | 判断理由 |
| --- | --- | --- | --- |
| 高 | 承認済み記憶から必要な原文へ戻る | 原文参照ID、版、発言範囲から限定読み出しするローカル経路 | 抽出時に落とした条件・例外を後から確認できる |
| 高 | 検索結果を小さくしてから返す | 抜粋・IDを先に返し、必要分のみ展開。各本文・合計量の上限と省略通知 | 人工データで件数制限だけでは不十分と確認 |
| 高 | 根拠の種類と由来を保つ | 発言/計画/操作結果、現行/取消、現在のチャット由来を返す | 古い発言や自分自身の引用を確定事実へ昇格させない |
| 中 | 絞り込みと追加検索の手順 | 既存の追加検索に原文検索を選択肢として追加 | 既にある機能を重複実装せず、必要な時だけ探索を増やす |
| 中 | 追記を差分で索引化 | 実測で読み直しが重いと分かった経路だけに導入 | 強い速度改善はあるが、書換検出との取引条件がある |

原文の常時全文保存、自由なJS/SQL実行の公開、英語限定のmemory検索は、現時点の採用候補にしない。
原文参照はローカルで閉じ、検索結果を確認済みの記憶と混ぜず、原文が消えた場合は参照不能と返す案を推奨する。
これは提案であり、既存の保存方針を変える決定ではない。
リポジトリのコードにはAGPL-3.0-onlyの表記がある。今回はコード移植を行っていない。

## 5. 取り込む前に測ること

1. 機密情報を除いた、期待する根拠と回答を固定できる質問を用意し、調整用と最終評価用を分ける。
2. 同じ質問・モデル・回答指示で「履歴なし」「既存OrgBrain」「原文検索」「既存OrgBrain+原文の追加読み出し」を比較する。
   同じ入力予算での比較と、予算を変えた比較を分ける。
3. 回答の正しさ、必要な根拠の回収、古い決定の誤採用、検索の実使用率を測る。
   コード作業では最終テストの成功を別に測る。
4. 親モデルと検索補助を含む全トークン・費用、待ち時間、返した文章量を記録する。
   日付・日本語・長いログ・修正された決定・回答不能・履歴内の命令文を含むケースも入れる。
5. 同じ問題ごとの結果を保存し、改善幅と不確実さを出す。
   検索だけの成功を、回答やコード修正の改善へ読み替えない。

原文参照の最小試作とこの比較が、次の実装候補。全履歴の常時保存から始める必要はない。
