# 実セッションでのObelisk試行とOrgBrain比較方法

2026-11-02。Obeliskは `1f8205b5b600516fe09ebea80d6983bcac1082b8`、Node v26.12.1。
上流CLIとCoreを変更せず実行した。製品への導入・設定変更・OrgBrainとの本比較は行っていない。

## 結果

実際のOrgBrainプロジェクトの履歴で、取り込みから検索、発言の前後の読み出しまで動作した。
有効な18問のうち、最初の語句検索で正解の報告本文に届いたのは6問。
日本語の部分一致・質問に含まれる日時・前後の発言を使う手順へ調整すると18問すべてに届いた。
この18問は調整にも使ったため、未知の質問に対する正答率100%という意味ではない。

実際に確認できた利点は、短い記憶だけでは落ちやすい数字・条件・訂正履歴へ戻れること。
課題は、日本語の検索手順が結果を大きく左右することと、候補から最終的な報告を選ぶ必要があること。
OrgBrainに対する優位性、独立した回答モデルの正答率、コーディング成功率、総トークンの削減効果は未測定。

## 対象と実行方法

| 項目 | 範囲 |
| --- | --- |
| 元データ | OrgBrainプロジェクトの実Codex履歴12ファイル、134,524,236バイト（約128.3 MiB） |
| セッション | 親チャット6件、子エージェント5件。継続分割1件を含む12ファイル |
| 時点 | 2026-11-02 09:00 JSTより前の記録。以後の68行を除外 |
| 除外 | この評価チャット、同日開始の他チャット、guardian監視用履歴、他プロジェクト |
| 索引 | 6セッション、3,386メッセージ、2,581ツール実行、2,581ツール結果、5子エージェント |
| 動かしたもの | 上流CLIの `--build` と `--query`。Coreの `search()`、`sql()`、`messages()` |
| 個人データの扱い | 原文・DB・検索結果本文は権限を限定した一時領域。外部モデルへ送信せず、Wikiへ原文を取り込まない |

ObeliskにはCLI用DBの保存先を指定する引数がないため、Nodeの起動フックで、このプロセス内の
`os.homedir()`だけを専用一時領域へ向けた。`HOME`と通常のObelisk設定・保存先は変更していない。
専用領域には選択したCodex履歴だけを置いた。CLIが返したDBの保存先もその領域に一致した。
これは隔離した開発用実行であり、アプリ導入や常駐監視の検証ではない。

## 質問と正解資料

原文の最終報告から20問を作り、質問・最初の検索語・参照する報告を固定してから検索した。
質問作成者は正解資料を読んでいる。最初の検索語にも人の判断が入っており、盲検評価ではない。
検索プログラムには正解の数値や出典メッセージIDを渡していない。
対象23報告が索引内にあり、元の報告本文と一致することを照合した。

採点前の日時確認で、2問に作問ミスが見つかった。

- q07: UTCの10月30日を日本時間の10月30日として質問したが、該当報告は10月31日00:36 JST。
- q08: 「朝」と質問したが、該当報告は10月31日13:53 JST。

この2問は両方式の集計から除外し、最初の質問・結果も残した。正解に合わせて結果を上書きしていない。
有効18問は、数値の再確認、設計案と採用済みの区別、後からの訂正、未検証事項、集計の分母などを含む。
履歴に根拠が全く存在しない質問と、実作業の再実行は含まない。

ここでの正解は「その時点のチャットで、何がどう報告されたか」。
過去の実行内容や現在の本番状態が実際に正しいことを、この試行で再証明したものではない。

## 検索手順ごとの確認結果

| 手順 | 正解の報告本文に届いた質問 | 条件 |
| --- | ---: | --- |
| 最初の語句検索 | 6/18 | 固定した2検索語、各上位5件。ヒット本文を対象とし、自動付加された近傍本文は採点対象外 |
| 部分一致・日時・前後参照を使った手順 | 18/18 | 同じ質問で調整。SQL部分一致の上位5件と前後の本文各1件を取得 |

後者では、1発言は最大1,800文字、1問の根拠本文合計は最大12,000文字とした。
実際の最大値は6,336文字。これは文字数の上限であり、回答モデルのトークン上限ではない。
2つの手順は使った処理と読み出し量も異なるため、検索エンジンだけの因果的な改善幅にはしない。

最初の20問の検索では、近傍を含む元の戻り値は合計347,968文字だった。
検索・整形処理の計測合計は55 msだが、CLIの開始、索引更新、モデルの推論は含まない。
単一回・ローカルの温まったデータでの確認なので、速度比較には使わない。

文字列の必須項目確認は補助とし、取得した報告を読み、18問の回答例が原文の条件と合うことも手動で確認した。
この確認も、同じ作成者による盲検でない確認。独立モデルの自動回答スコアとは区別する。

### 根拠付きで再確認できた例

| 質問 | 取得した当時の報告 |
| --- | --- |
| `wiki_busy`の直接原因は分かったか | ロックの取得待ちは約5秒。直接原因は未特定で、再発防止の修正も未実施 |
| 削除できないと言っていたworktreeは最後にどうなったか | 後に通常のGit手順で削除完了。以前の説明を訂正 |
| 提案2件は採用済みの判断として保存したか | 採用未確認の提案として保存 |
| 315テスト成功なら実モデルの抽出・再利用も確認済みか | テストの推論はモック。実抽出は予算で保留、効果は未検証 |
| 0/82の82はタスク数か | タスク数ではなく、評価済みの記憶参照数 |

これらの根拠へ戻れることは確認できた。一方、古い報告と訂正後の報告が両方返る場合は、
回答側が質問の時点と出典を確認する必要がある。保存量の多さだけで正しい結論は保証されない。

## OrgBrainと比較する方法

### 1. 同じ資料での比較と、現在の製品状態での比較を分ける

| 比較 | そろえるもの | 分かること |
| --- | --- | --- |
| 現在の利用状態 | 同じ質問・回答モデル。各製品が現在持つ資料の範囲を別途記録 | 普段使いでどちらが答えやすいか。保存範囲の差も含む |
| 同じ原資料 | 同じ時点のセッションを隔離環境へ渡し、各製品の本来の保存・検索経路を使う | 同じ原資料から記憶を作り、取り出す仕組みの差 |

OrgBrainは選別した記憶、Obeliskは履歴の広い索引を使うため、片方だけに原資料がある問題を
「検索精度の負け」とまとめない。全問での結果と、両方が必要情報を保持していた問題の結果を分ける。
OrgBrainの取り込み・審査・索引の準備費も記録し、Obeliskの索引作成費と分けて比較する。
予算やoff設定を評価のために解除しない。

### 2. 今回の18問は調整用として残し、未使用の質問を作る

次の比較では、今回と別のチャットから最低30問を用意する案とする。
判断理由、失敗と修正、変更・訂正、細かい数値と条件、回答不能を各6問ずつ。
数字の暗記だけに寄せず、再利用したい判断・手順も同じ比重で入れる。
複数チャット・可能なら複数プロジェクトへ広げる。

資料担当が質問・必須事実・許容する回答・根拠位置・時点を先に固定する。
検索・回答を行う側には正解を見せない。日時はUTCとJSTを両方記録する。
この試行の質問・回答・評価結果を、新しい原資料や検索対象へ混入させない。

### 3. 回答側の条件をそろえる

```text
同じ質問
  ├─ 履歴なし ────────── 同じ回答モデル・別の新規文脈
  ├─ Obelisk ─────────── 同じ回答モデル・別の新規文脈
  └─ OrgBrain ─────────── 同じ回答モデル・別の新規文脈
```

同じモデル、回答指示、出力形式、根拠の入力上限で実行する。
最初の案は、根拠入力8,000トークン、検索最大3回、追加読み出し最大5回。
Obeliskは今回調整した日本語・期間・近傍の手順を使う。OrgBrainも現行の推奨経路を使い、
両者の手順を最終評価前に固定する。質問ごとの都合で検索回数を増やさない。
実行順は入れ替え、他方の答えや正解を見た会話履歴を引き継がない。

### 4. 検索と回答を別に採点する

| 指標 | 確認すること |
| --- | --- |
| 根拠の取得 | 必要な条件・例外・時点を含む原文に届いたか |
| 回答の正しさ | 必須事実がそろい、根拠のない主張を足していないか |
| 古い情報の誤採用 | 取り消しや後の訂正を見落としていないか |
| 回答不能の判断 | 情報がないときに作り話をせず、情報があるときに不明で済ませていないか |
| 費用と待ち時間 | 検索、注入、回答、補助モデル、失敗・再実行を含む総量 |

「正答」「一部不足」「誤答」「適切な回答不能」「誤った回答不能」を分ける。
同じ質問ごとの結果を並べ、優劣だけでなく何問が変わったかを出す。
同じチャットの質問は互いに似やすいため、チャット単位の偏りも確認する。
使用量の未取得はnull等で残し、報告された0と区別する。
モデルの全入力・出力・キャッシュを含め、準備費と1質問あたりの費用を別記する。

### 5. 最後に小さな実作業で確認する

履歴QAで良くても、コード修正や調査再開が速くなるとは限らない。
QA後、隔離した修正・調査・文書更新の課題を別に用意し、最終成果・テスト成功・総費用を比較する。
原文検索をOrgBrainへ足す案は、この段階で第3の方式として評価できる。

## 追加確認: 保存容量と増加への対策

同じ固定済み履歴で、元データと索引DBを別に測定した。

| 対象 | 容量 |
| --- | ---: |
| 元履歴12ファイル | 134,524,236バイト（約134.5 MB） |
| 追加されるSQLite DB本体 | 26,083,328バイト（約26.1 MB） |
| 元履歴＋DB本体 | 160,607,564バイト（約160.6 MB） |

このほか共有メモリ用ファイルは32,768バイト、WALは測定時0バイト。
DB本体は元履歴の約19.4%だが、これはこのCodex資料での値。
DBは検索用に投影・切り詰めたデータであり、元ログを置き換える可逆圧縮ではない。
元データには索引へ入れない記録もあるので、他の履歴でも同じ割合になるとは言えない。

確認した対策は次のとおり。

- **1件あたりの本文量を制限**: 共通処理の本文は最大10,000 UTF-16コード単位。
  Codexの発言・ツール結果にこの処理を使う。JSON入力は含まれる各文字列の制限であり、
  レコード全体が必ず10,000文字以内になるわけではない。必要な先の部分は元記録へ戻って読む。
- **全文検索の本文コピーを抑制**: `messages_fts`は`content=messages`を使う。
  SQLiteの外部コンテンツ方式なので、本文は元の表から読み、検索表にもう1部の全文コピーを置かない。
- **同じIDの更新を重複追加しない**: 永続化はIDを使った更新で、再読み込み時に内容が同じ行への書き込みも省く。
  別IDの同じ文章を意味に基づいて自動統合するという意味ではない。
- **更新・読み出しの仕事を抑える**: 追記部分の取り込み、索引検索、期間・プロジェクトの条件、件数制限、
  前後の有限窓がある。これらは処理時間とAIへ渡す量の対策であり、履歴の総量の上限ではない。

通常の監視経路の追記は差分だけを読めるが、CodexのCLI検索前の更新確認は厳格モードを使い、
既存部分を検証のために読み直す経路がある。「検索のたびに履歴のサイズと無関係な負荷」とは扱わない。
また、検索の件数制限だけでは合計文字数は十分に制限されないことを、前回の人工データで確認している。

Core・CLI・アプリのメイン処理・設計資料を調べた範囲では、保存期限による自動削除、全体容量の上限、
古いセッションの自動要約置き換え、DB全体の自動圧縮によって総量を一定にする機能は確認できなかった。
元データの削除や置き換えに索引を合わせる処理はあるが、容量や経過日数による整理とは別である。
DeepSeekの圧縮済み形式を読む対応も、Obelisk自身が全履歴を圧縮して管理する機能とは区別する。

今回のDBで大きかったのはツール結果約13.4 MBとツール入力約5.9 MB。
長期利用では実行ログと件数の増加も見る必要がある。長期間の容量増加や大規模時の速度は未測定。
[容量の測定値](../artifacts/obelisk-real-session-20261102/storage-measurement.json)を保存した。

## 追加確認: 元のセッションを削除した場合

同じ版の上流CLIで、実Codexセッション1件のコピーだけを専用の使い捨て領域へ取り込み、
コピーを削除して検証した。通常の更新を確実に通すため、このテストDBだけで30秒の更新間隔制限を解除した。
実際の元ファイルと前の評価用スナップショットは、変更前後のハッシュ一致を確認した。
残存確認用の記憶1件は、この試験のための架空のメモであり、実ユーザーの結論を新たに保存したものではない。

| 状態 | 索引内メッセージ | 検索ヒット | 元記録への読み戻し | 別登録の記憶 |
| --- | ---: | ---: | --- | ---: |
| 削除前 | 18件 | 2件 | 成功 | 1件 |
| 個別ログ削除後、通常の検索前更新 | 18件 | 2件 | 不可 | 1件 |
| その後、`--build`で完全再構築 | 0件 | 0件 | 不可 | 1件 |

このCodex経路では、個別ログの削除だけでは通常更新が既存の索引行を消さない。
そのため検索できる内容は残るが、元ファイルを読む`raw()`は即座に使えなくなる。
完全再構築は、読み取れる現在の原資料からセッション・発言等を作り直すので、削除済みログの索引は消える。
`memories`と、そのメモのMarkdownファイルは別に保持された。出典セッションへの参照先は失われる。
元ログの削除だけで、Obelisk側の情報もすべて消えたと扱ってはいけない。

保存フォルダ全体を一時的に見えなくする場合も追加確認した。
通常更新は既存18メッセージ・2ヒット・記憶1件を保持し、元記録への読み戻しは失敗した。
この状態の完全再構築は`incomplete_snapshot: Source folder is unavailable`で拒否された。
単なる保存先の一時的な不在を、履歴をすべて消してよい状態と扱わない保護である。

試験前後のDB本体は450,560バイトで同じだった。検索から行が消えることと、DBファイルが縮むこと、
媒体上からの安全な消去は別である。後者の安全な消去は検証していない。
以上はこの版のCodexでの結果であり、他provider・アプリの監視経路へ一律には一般化しない。
