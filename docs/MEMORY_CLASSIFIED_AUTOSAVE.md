# 分類が明確な記憶の自動保存

ローカルの通常保存は、記憶の種類が明確ならモデルによる審査を待たずに保存する。
成功の記録は fact / org_knowledge、失敗の記録は pitfall として扱う。
「判断」と抽出された内容も原文を参照し、ユーザーの明示的な選択・指示や、
該当する提案への明示的な承諾が確認できる場合だけ decision とする。
提案や技術説明・見込みは fact として、採用状況を付けて保存する。
短期履歴は既存の episodic 区分を使う。
種類の不明・不一致・明示的な分類の曖昧さ、またはプロジェクトの未確定がある
候補だけを審査待ちに残す。分類には保存対象となる本文も必要。

## 設定と適用範囲

- `ORGBRAIN_MEMORY_AUTO_SAVE_CLASSIFIED` は既定で有効。
  一時的に元の審査経路へ戻すときは `false` を指定する。
- 共通セッション抽出ワーカー、Codex Stop のローカル保存、ローカル MCP の
  learning batch、Wiki/セッションの source intake に適用する。
- `memory_learning_mode=off` は保存しない。`confirm` の本人確認手順、
  インタラクティブな propose/confirm、対象プロジェクト、月間予算は維持する。
- Cloud サーバーの保存規則や既存の審査待ち候補は一括変更しない。

## 保存と検証の区別

`memory-classified-autosave.mjs` が種類と本文を判定し、
`TaskCommitmentStore.saveLearningCandidates({autoSaveClassified:true})` が
`LocalMemoryStore.captureIntoDatabase` を通して本文・検索用データを同一の
トランザクションで保存する。明確な候補は審査待ちテーブルに追加しない。
同じ source / external_key は重複作成しない。

## 提案と採用済み判断

分類ポリシーは `classified-auto/v2`。共通セッション抽出では、保持済み原文
パケットの役割・順序・引用位置・ハッシュを保存時にも使う。質問、引用された
指示、toolの本文、assistantだけの提案を、本人の採用根拠にはしない。
「その案で進めて」のような承諾は、直前の該当提案と結び付く場合だけ使う。
複数案のどれを指すか不明な承諾や、別件の承諾では採用済みにしない。
ユーザーの承諾にある条件と、承諾された提案の条件も保存する。

原文がない経路では、検証器が実際のuser原文と照合した証拠がある場合に限って
選択の根拠を使う。分類ラベルやAIが付けたメタデータだけでは採用済みにしない。
採用の根拠がない提案は `proposal / unconfirmed`、説明は `source-report`、
見込みは `hypothesis` として保存できる。情報不足で種類を決められない候補は
審査待ちに残す。採用の確認と、実装完了・実行成功の確認は別に扱う。

## 重複の統合

テナント、プロジェクト、作業区分、業務分類、公開範囲、検証状態、出典の区分、
本文、理由、再利用条件、適用先、採用状態が一致する記憶を統合する。
本文のコードの空白・条件・例外を削って同一視したり、意味が似ているだけで
統合したりはしない。提案と採用済み判断、異なる条件・バージョン・プロジェクトは別にする。

統合時は元の記憶IDを使い、出典・証拠・発生イベントの識別情報を追加して検索用
データも更新する。再起動や別イベントの再抽出でも同じ判定を使う。既存の検証状態を
自動で引き上げず、重複を根拠に有効期限も延長しない。最大4096件の出典・証拠を保持し、
それを超える場合は原本を落とさず別記憶として保存する。既存記憶の一括再分類は行わない。

分類だけで検証済みにはしない。新しい自動保存は `verification_state=unverified`
とし、`reported_verification` や元の不足情報も残す。秘密情報の除外、
保存時の本文改変検出、出典の版・ハッシュ・参照照合は維持する。
Source intake で既に有効な同一原本がある場合は再抽出せず、その結果を返す。

設定変更が必要なのは、明確な種類まで一律に審査待ちとなる場合。
事実確認や過去の実行証明が必要な場合は、保存済みという状態から推定せず、
原本と実行結果を別に確認する。

## 検証

`scripts/memory-classified-autosave.test.mjs` は即時保存、分類不一致、秘密情報、
重複統合、出典の保持、未検証状態の維持、原本変更の拒否を検証する。
提案・直接の選択・条件付き承諾・複数案への曖昧な承諾・別件の承諾・引用された指示・
採用メタデータの偽装も検証する。重複のテストは再起動、別条件、別プロジェクト、
64件を超える出典、ネイティブStop保存とsource intakeを含む。
`scripts/memory-pipeline-cli-reuse.test.mjs` は既定の CLI で審査モデルが
起動しないことと、無効化時の従来経路を検証する。
共通ワーカーと実 CLI Stop の自動起動テストは隔離 DB とモック API を使う。
これらは実モデルによる分類精度や実会話の次回 Stop を証明するものではない。
